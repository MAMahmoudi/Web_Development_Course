Lab 10: Securing your web application

Instructions

In this lab, your team performs a hands-on security audit of its own project. For every web service (each CRUD operation), you will look for the most common web vulnerabilities: SQL injection, Cross-Site Scripting (XSS), Cross-Site Request Forgery (CSRF), weak password storage, insecure sessions, missing authorization checks, unsafe file uploads and leaked secrets. You will fix what you find, record everything in an audit report, and finally audit another team's project. The theory behind this lab is covered in the lectures Security and Sessions and Cookies; read them before you start.

I. Preparing the audit

A security audit is a systematic review: you do not just "look around", you list every entry point of your application and check each one against the same list of attacks. An entry point is anything that receives data from the user: a form, a URL parameter (?id=), a cookie, an uploaded file or an AJAX request. Remember the golden rule from the lecture: never trust user input, and that includes the data sent by your own JavaScript, because anyone can modify or replay a request with the browser DevTools.

Step 1: list your services and entry points

Create a branch for the audit and a file SECURITY_AUDIT.md at the root of your repository. In this file, list each of your (at least 5) web services, the PHP file(s) that implement it, the HTTP method, the parameters it receives and who is allowed to use it (visitor, logged-in user, owner, admin). 

git checkout main
git pull
git checkout -b security-audit
# create SECURITY_AUDIT.md, then commit it
git add SECURITY_AUDIT.md
git commit -m "Add security audit inventory of web services"
        
# Security audit - Team X

| Service           | File(s)                    | Method | Parameters              | Allowed users   |
|-------------------|----------------------------|--------|-------------------------|-----------------|
| Create a product  | products/create.php        | POST   | name, price, image      | admin           |
| List products     | products/list.php (AJAX)   | GET    | q, page                 | everyone        |

Important: all the attack examples of this lab must be tried only on your own local copy (XAMPP on your machine) or on a copy of a classmate's project they agreed to share with you. Attacking a real website without written permission is illegal.

II. SQL injection

SQL injection happens when user input is pasted directly into the text of an SQL query. The attacker then writes SQL instead of data and changes the meaning of the query. Search your code for every query built with string concatenation or variables inside a double-quoted string ("... '$email' ...").

The vulnerable version

<?php
// login.php - VULNERABLE, do not use
$email    = $_POST['email'];
$password = $_POST['password'];

$conn = mysqli_connect('localhost', 'root', '', 'shop');
$sql  = "SELECT * FROM users WHERE email = '$email' AND password = '$password'";
$result = mysqli_query($conn, $sql);

if (mysqli_num_rows($result) > 0) {
    echo 'Welcome!';
}

Try it on your local copy: type ' OR '1'='1' -- (with a space after the two dashes) in the email field and anything in the password field. The query becomes SELECT * FROM users WHERE email = '' OR '1'='1' -- ' AND password = '...': the condition is always true and the rest is a comment, so you are logged in without knowing any password. The same trick can be used to read or delete whole tables.

The fix: PDO prepared statements

With a prepared statement, the query and the data are sent separately to MySQL. The query contains placeholders (? or :name) and the values are bound later, so they can never be interpreted as SQL. Put the connection in a single file that every service includes. 

<?php
// includes/db.php - one shared connection for the whole project
$config = require __DIR__ . '/../config.php'; // see section VII (secrets out of Git)

$pdo = new PDO(
    "mysql:host={$config['db_host']};dbname={$config['db_name']};charset=utf8mb4",
    $config['db_user'],
    $config['db_pass'],
    [
        PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,
        PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
        PDO::ATTR_EMULATE_PREPARES   => false,
    ]
);
        
<?php
// login.php - SAFE
require __DIR__ . '/includes/db.php';

$email    = trim($_POST['email'] ?? '');
$password = $_POST['password'] ?? '';

$stmt = $pdo->prepare('SELECT id, name, role, password_hash FROM users WHERE email = ?');
$stmt->execute([$email]);
$user = $stmt->fetch();

if ($user && password_verify($password, $user['password_hash'])) {
    // login succeeded (see section V for the session part)
} else {
    $error = 'Invalid email or password.';
}

// Named placeholders work too:
$stmt = $pdo->prepare('UPDATE products SET name = :name, price = :price WHERE id = :id');
$stmt->execute(['name' => $name, 'price' => $price, 'id' => $id]);
Tip: placeholders can only replace values, not table or column names. If the user chooses a sort column (?sort=price), check it against a whitelist: $sort = in_array($_GET['sort'] ?? '', ['name', 'price', 'created_at'], true) ? $_GET['sort'] : 'name';. If your project uses mysqli instead of PDO, use mysqli_prepare() and mysqli_stmt_bind_param(); the principle is the same.

III. Cross-Site Scripting (XSS)

XSS happens when user data is inserted into a page as HTML, so the browser executes it. In a reflected XSS, the payload comes from the current request (for example a search term in the URL) and is echoed back. In a stored XSS, the payload is saved in the database (a comment, a username, a product description) and executed for every visitor who views it. The injected script runs with the victim's session: it can read the page, send requests in their name or redirect them.

Find the problem

<?php
// search.php - VULNERABLE (reflected XSS)
echo "<p>Results for: " . $_GET['q'] . "</p>";

// product.php - VULNERABLE (stored XSS)
foreach ($reviews as $review) {
    echo "<div class='review'><b>{$review['author']}</b>: {$review['text']}</div>";
}

Test it locally: open search.php?q=<script>alert(1)</script>, and post a review whose text is <img src=x onerror="alert(document.cookie)">. If an alert box appears, the service is vulnerable.

The fix in PHP: escape on output

Store the data as the user typed it, but escape it every time you print it in HTML with htmlspecialchars($value, ENT_QUOTES, 'UTF-8'). This converts < > & " ' into HTML entities, so the browser displays them as text. ENT_QUOTES is required to protect attribute values written between single quotes. Define a short helper and use it everywhere. 

<?php
// includes/functions.php
function e(?string $value): string
{
    return htmlspecialchars($value ?? '', ENT_QUOTES, 'UTF-8');
}
        
<?php require __DIR__ . '/includes/functions.php'; ?>
<p>Results for: <?= e($_GET['q'] ?? '') ?></p>

<?php foreach ($reviews as $review): ?>
  <div class="review">
    <b><?= e($review['author']) ?></b>: <?= e($review['text']) ?>
  </div>
<?php endforeach; ?>

<input type="text" name="name" value="<?= e($product['name']) ?>">

The fix in JavaScript: textContent instead of innerHTML

Your AJAX services return JSON, and the escaping must then happen in JavaScript. Never put user data in innerHTML (or jQuery's .html(), or insertAdjacentHTML). Create the elements and assign the data with textContent (or jQuery's .text()), which never interprets HTML. 

// VULNERABLE: the review text is parsed as HTML
list.innerHTML += `<li><b>${review.author}</b>: ${review.text}</li>`;

// SAFE: the data is inserted as plain text
const li = document.createElement('li');
const author = document.createElement('b');
author.textContent = review.author;
li.append(author, ': ' + review.text); // append() with a string creates a text node
list.appendChild(li);

// SAFE with jQuery
$('<li>').append($('<b>').text(review.author), document.createTextNode(': ' + review.text)).appendTo('#list');
Tip: escaping is also needed in URLs and in links. A user-supplied link such as javascript:alert(1) is dangerous inside href even after htmlspecialchars; accept only links that start with https:// or http://. The Content-Security-Policy header of section VII adds a second layer of protection.

IV. Cross-Site Request Forgery (CSRF)

The browser automatically sends your session cookie with every request to your site, even when the request is triggered by another website. A malicious page can therefore contain a hidden form that posts to http://localhost/project/products/delete.php: if an admin visits that page while logged in, the product is deleted with the admin's rights. The defense is a secret token that the attacker's page cannot know: it is stored in the session and must be sent back with every request that changes data.

Generate one token per session

<?php
// includes/csrf.php (include it after session_start())
function csrf_token(): string
{
    if (empty($_SESSION['csrf_token'])) {
        $_SESSION['csrf_token'] = bin2hex(random_bytes(32)); // 64 hexadecimal characters
    }
    return $_SESSION['csrf_token'];
}

function csrf_check(): void
{
    $sent = $_POST['csrf_token'] ?? $_SERVER['HTTP_X_CSRF_TOKEN'] ?? '';
    if (!is_string($sent) || !hash_equals(csrf_token(), $sent)) {
        http_response_code(403);
        exit('Invalid CSRF token.');
    }
}

Add the token to every form and check it

<form action="products/delete.php" method="post">
  <input type="hidden" name="csrf_token" value="<?= e(csrf_token()) ?>">
  <input type="hidden" name="id" value="<?= (int) $product['id'] ?>">
  <button type="submit">Delete</button>
</form>
        
<?php
// products/delete.php
session_start();
require __DIR__ . '/../includes/csrf.php';

if ($_SERVER['REQUEST_METHOD'] !== 'POST') {
    http_response_code(405);
    exit('Method not allowed.');
}
csrf_check();
// ... authorization check (section V), then the DELETE query

AJAX requests

For AJAX, print the token once in a <meta> tag and send it in a custom header. csrf_check() above already reads $_SERVER['HTTP_X_CSRF_TOKEN']. 

// In the page head: <meta name="csrf-token" content="<?= e(csrf_token()) ?>">
const token = document.querySelector('meta[name="csrf-token"]').content;

fetch('products/delete.php', {
  method: 'POST',
  headers: { 'X-CSRF-Token': token },
  body: new URLSearchParams({ id: productId })
})
  .then(response => response.json())
  .then(data => console.log(data));
Rules: (1) actions that change data (create, update, delete, logout) must never be done with a GET request or a simple link; (2) compare tokens with hash_equals(), not ==, to avoid timing attacks; (3) set the session cookie with SameSite=Lax (or Strict, see section V): modern browsers then do not send it with cross-site POST requests, which is a second layer of protection, not a replacement for the token.

V. Passwords, sessions and authorization

Password storage

Passwords must never be stored in clear text, nor with fast hashes such as md5() or sha1(), which can be cracked by billions of guesses per second. Use password_hash(), which applies a slow algorithm (bcrypt by default) with a random salt, and password_verify() to check a login. The result is up to 255 characters long, so the column should be VARCHAR(255). 

ALTER TABLE users CHANGE password password_hash VARCHAR(255) NOT NULL;
        
<?php
// register.php
$hash = password_hash($_POST['password'], PASSWORD_DEFAULT);
$stmt = $pdo->prepare('INSERT INTO users (name, email, password_hash) VALUES (?, ?, ?)');
$stmt->execute([$name, $email, $hash]);

// login.php (after fetching $user with a prepared statement)
if ($user && password_verify($_POST['password'], $user['password_hash'])) {
    if (password_needs_rehash($user['password_hash'], PASSWORD_DEFAULT)) {
        $newHash = password_hash($_POST['password'], PASSWORD_DEFAULT);
        $pdo->prepare('UPDATE users SET password_hash = ? WHERE id = ?')->execute([$newHash, $user['id']]);
    }
    // ... start the authenticated session (below)
}
Tip: if your database already contains clear-text passwords, write a small one-time script that replaces each of them with password_hash(), or simply recreate your test accounts. Show the same message ("Invalid email or password") whether the email or the password is wrong.

Session security

The session cookie is the key to the account: if an attacker steals it, they are logged in. Configure the cookie before session_start(), regenerate the session id at login (to prevent session fixation), expire inactive sessions and destroy the session completely at logout. See the "Securing Session INI Settings" part of the Security lecture for the meaning of each option. 

<?php
// includes/session.php - include this file at the top of EVERY page instead of calling session_start()
ini_set('session.use_strict_mode', '1');
ini_set('session.use_only_cookies', '1');

session_set_cookie_params([
    'lifetime' => 0,                                   // cookie deleted when the browser closes
    'path'     => '/',
    'secure'   => !empty($_SERVER['HTTPS']),           // true as soon as the site uses HTTPS
    'httponly' => true,                                // not readable from JavaScript (document.cookie)
    'samesite' => 'Lax',
]);
session_start();

const SESSION_TIMEOUT = 1800; // 30 minutes of inactivity

if (isset($_SESSION['last_activity']) && time() - $_SESSION['last_activity'] > SESSION_TIMEOUT) {
    session_unset();
    session_destroy();
    header('Location: login.php?expired=1');
    exit;
}
$_SESSION['last_activity'] = time();
        
<?php
// login.php, after password_verify() succeeded
session_regenerate_id(true); // new id, old session file deleted
$_SESSION['user_id'] = $user['id'];
$_SESSION['role']    = $user['role'];

// logout.php (called with POST + CSRF token)
$_SESSION = [];
setcookie(session_name(), '', ['expires' => time() - 3600, 'path' => '/']);
session_destroy();
header('Location: index.php');
exit;

Authorization on every action (IDOR)

Authentication answers "who are you?"; authorization answers "are you allowed to do this?". A very common bug is the Insecure Direct Object Reference (IDOR): the page edit_post.php?id=42 shows your post, but if you change the URL to ?id=43 you can edit somebody else's post, because the server only checks that you are logged in. Hiding a button in the interface is not a protection: the check must be done in PHP, in every service, both when the form is displayed and when it is submitted. 

<?php
// includes/auth.php
function require_login(): int
{
    if (empty($_SESSION['user_id'])) {
        header('Location: login.php');
        exit;
    }
    return (int) $_SESSION['user_id'];
}

function require_role(string $role): void
{
    require_login();
    if (($_SESSION['role'] ?? '') !== $role) {
        http_response_code(403);
        exit('Access denied.');
    }
}
        
<?php
// edit_post.php
require __DIR__ . '/includes/session.php';
require __DIR__ . '/includes/auth.php';
require __DIR__ . '/includes/db.php';

$userId = require_login();
$postId = filter_input(INPUT_GET, 'id', FILTER_VALIDATE_INT);

// VULNERABLE: any logged-in user can open any post
// $stmt = $pdo->prepare('SELECT * FROM posts WHERE id = ?');
// $stmt->execute([$postId]);

// SAFE: the post must belong to the current user
$stmt = $pdo->prepare('SELECT * FROM posts WHERE id = ? AND user_id = ?');
$stmt->execute([$postId, $userId]);
$post = $stmt->fetch();

if (!$post) {
    http_response_code(404);
    exit('Post not found.');
}

// The same condition must appear in the UPDATE / DELETE query:
// UPDATE posts SET title = ?, body = ? WHERE id = ? AND user_id = ?
Test: create two test accounts, A and B. Log in as A, copy the URL or the AJAX request (DevTools > Network > right click > "Copy as fetch") of each edit or delete action, log in as B and replay it. Every one of these attempts must fail.

VI. File upload hardening

If your project accepts files (profile pictures, product images, documents), an attacker may upload a file named shell.php and then open it in the browser: Apache will execute it and the attacker controls your server. Never trust the file name or the type sent by the browser ($_FILES['x']['type']), both are chosen by the client. Instead: check the upload error and the size, detect the real type from the content, generate a new random name with an extension you choose, and forbid script execution in the upload folder. 

<?php
// upload_avatar.php (session, CSRF and login checks done before)
$allowed = [
    'image/jpeg' => 'jpg',
    'image/png'  => 'png',
    'image/webp' => 'webp',
];
$maxSize = 2 * 1024 * 1024; // 2 MB

$file = $_FILES['avatar'] ?? null;
if (!$file || $file['error'] !== UPLOAD_ERR_OK) {
    exit('Upload failed.');
}
if ($file['size'] > $maxSize) {
    exit('File too large (2 MB maximum).');
}

$finfo = new finfo(FILEINFO_MIME_TYPE);
$mime  = $finfo->file($file['tmp_name']); // real type, read from the file content
if (!isset($allowed[$mime])) {
    exit('Only JPEG, PNG and WebP images are accepted.');
}

$newName = bin2hex(random_bytes(16)) . '.' . $allowed[$mime];
$target  = __DIR__ . '/uploads/' . $newName;

if (!move_uploaded_file($file['tmp_name'], $target)) {
    exit('Could not save the file.');
}

$stmt = $pdo->prepare('UPDATE users SET avatar = ? WHERE id = ?');
$stmt->execute([$newName, $userId]);

Then add an .htaccess file inside the uploads/ folder so that, even if a script gets there, Apache refuses to serve it and does not list the folder content. 

# uploads/.htaccess
Options -Indexes
<FilesMatch "\.(php|phtml|phar|php\d)$">
    Require all denied
</FilesMatch>
Tip: the finfo class comes from the fileinfo extension. If you get "Class finfo not found", open php.ini from the XAMPP control panel (Apache > Config), remove the ; in front of extension=fileinfo and restart Apache. Also add a client-side check (accept="image/*", size check in JS) for a better user experience, but remember it is not a security measure.

VII. Errors, security headers and secrets

Do not display errors in production

PHP error messages and uncaught PDO exceptions reveal file paths, SQL queries and sometimes credentials. They are very useful during development, but on a deployed site they must be written to a log file only, and the user must see a generic message. 

; php.ini on the production server
display_errors = Off
display_startup_errors = Off
log_errors = On
error_reporting = E_ALL
        
<?php
// includes/bootstrap.php - if you cannot edit php.ini on your hosting
$isProduction = true; // read it from config.php in practice
ini_set('display_errors', $isProduction ? '0' : '1');
ini_set('log_errors', '1');
error_reporting(E_ALL);

// Around database operations:
try {
    $stmt = $pdo->prepare('INSERT INTO orders (user_id, total) VALUES (?, ?)');
    $stmt->execute([$userId, $total]);
} catch (PDOException $ex) {
    error_log($ex->getMessage());          // details go to the log file
    http_response_code(500);
    echo json_encode(['error' => 'Server error, please try again later.']);
    exit;
}

Security headers

HTTP response headers tell the browser to enable extra protections:

Header Protection
Content-Security-Policy Lists the sources from which scripts, styles, images, etc. may be loaded. Inline scripts are blocked, which stops most XSS payloads. frame-ancestors 'none' forbids other sites from embedding your pages in an iframe (clickjacking).
X-Content-Type-Options: nosniff Stops the browser from guessing the type of a file (for example executing an uploaded text file as JavaScript).
X-Frame-Options: DENY Older equivalent of frame-ancestors 'none', still useful for old browsers.
Referrer-Policy: strict-origin-when-cross-origin Avoids leaking full URLs (with their parameters) to other websites. 
<?php
// includes/headers.php - include at the top of every page, before any output
header("Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.jsdelivr.net; "
    . "style-src 'self' https://cdnjs.cloudflare.com; font-src 'self' https://cdnjs.cloudflare.com; "
    . "img-src 'self' data:; frame-ancestors 'none'; base-uri 'self'; form-action 'self'");
header('X-Content-Type-Options: nosniff');
header('X-Frame-Options: DENY');
header('Referrer-Policy: strict-origin-when-cross-origin');

The same headers can be set for the whole project (including HTML, CSS and JS files) in an .htaccess file at the root of the project (module mod_headers, enabled by default in XAMPP): 

# .htaccess at the project root
<IfModule mod_headers.c>
    Header always set Content-Security-Policy "default-src 'self'; script-src 'self' https://cdn.jsdelivr.net; style-src 'self' https://cdnjs.cloudflare.com; font-src 'self' https://cdnjs.cloudflare.com; img-src 'self' data:; frame-ancestors 'none'; base-uri 'self'; form-action 'self'"
    Header always set X-Content-Type-Options "nosniff"
    Header always set X-Frame-Options "DENY"
    Header always set Referrer-Policy "strict-origin-when-cross-origin"
</IfModule>
Options -Indexes
Warning: adapt the CSP to the CDNs your project really uses, then open every page with the DevTools console open: blocked resources are reported there. With this policy, <script>...</script> blocks inside the HTML and attributes such as onclick="..." stop working: move that code to external .js files and use addEventListener(). Check the result with the Network tab (Response headers).

Secrets out of the Git repository

Database passwords, API keys and SMTP passwords must not be committed: anyone with access to the repository (or to a public fork) can read them, and they stay in the Git history forever. Put them in a config.php file that is ignored by Git, and commit a config.example.php with fake values so that your teammates know which keys to fill. 

<?php
// config.example.php - committed. Copy it to config.php and fill in your own values.
return [
    'db_host' => 'localhost',
    'db_name' => 'your_database',
    'db_user' => 'root',
    'db_pass' => '',
    'production' => false,
];
        
# .gitignore
config.php
uploads/*
!uploads/.htaccess
*.log
        
# If config.php was already committed: stop tracking it (the local file is kept)
git rm --cached config.php
git add .gitignore config.example.php
git commit -m "Move database credentials to an ignored config.php"
Important: git rm --cached does not remove the file from the previous commits. If a real password was ever pushed, consider it public and change it.

Fill the checklist for each service

Copy the table below into SECURITY_AUDIT.md once per web service. For each line, write Pass, Fail or N/A (not applicable, with a reason). For every Fail, open a GitHub issue, fix it on your security-audit branch, and write the commit hash in the last column.

Peer review: audit another team's project

A fresh pair of eyes always finds problems the authors missed. Your teacher will pair the teams. Then:

  1. Each team gives the other team read access to its repository (or the URL if it is public) and the .sql dump of its database.
  2. Clone the other project, install it on your own XAMPP and make it work (this is also a test of their README and setup instructions).
  3. For about 45 minutes, go through the checklist above on their services. Use only your local copy.
  4. For each problem found, open an issue on their repository with the label security: the service, the steps to reproduce, the impact, and a suggested fix. Be precise and constructive; do not publish working exploits outside the issue.
  5. Each team then fixes the issues it received and closes them with a commit message such as Fix IDOR in edit_post.php (closes #12).
Tip: classify each finding by severity to decide what to fix first: High (SQL injection, missing authorization, executable uploads, leaked passwords), Medium (XSS, CSRF, session issues), Low (missing headers, verbose errors).

Deliverables

  • A SECURITY_AUDIT.md file at the root of the repository with the inventory of your services and one completed checklist table per service.
  • All the fixes committed on the security-audit branch and merged into main through a pull request; each fix linked to its issue.
  • The issues opened on the other team's repository during the peer review, and the issues you received fixed or answered.
  • config.php ignored by Git and config.example.php committed.
  • This work counts toward the "PHP/AJAX: Finish the backend" milestone in the Deadlines table of the Syllabus.
