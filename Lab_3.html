Lab 3: Responsive design (CSS part 2)

Instructions

In this lab, you will make the pages of your team project look good and work well on every screen: phones, tablets, laptops and large monitors.
You will use a mobile-first approach, the viewport meta tag, relative units, media queries, and Flexbox/Grid layouts that reflow. You will also make your images responsive and build a navigation bar that collapses into a hamburger menu on small screens.
Finally, you will learn how to test your pages with the device mode of your browser's DevTools.
Before you start, review the lecture CSS Layout (Flexbox, Grid and the responsive design part at the end), and keep the Lab 2 demo site open: it is responsive, and we will study its code throughout this lab.

I. What is responsive design?

A responsive website has a single HTML code base whose layout adapts to the size of the screen. We do not build a separate "mobile site". Responsive design rests on three ideas:

  1. Mobile first: write the styles for the smallest screen first, then add styles for larger screens.
  2. Fluid layouts: containers use relative sizes (%, rem, fr, ...) and Flexbox/Grid, so they stretch and shrink with the viewport instead of having a fixed width.
  3. Media queries: the @media at-rule applies a group of styles only when a condition is true (for example "the viewport is at least 768px wide"). The width where the layout changes is called a breakpoint.

1. The viewport meta tag

Without this tag, a mobile browser assumes that your page was designed for a desktop. It renders the page in a virtual window about 980px wide and then zooms out, so the text becomes tiny and your media queries never trigger. Every page of your project must have this line in its <head>: 

<head>
  <meta charset="UTF-8" />
  <meta name="viewport" content="width=device-width, initial-scale=1.0" />
  ...
</head>

width=device-width makes the layout viewport as wide as the device's screen (in CSS pixels). initial-scale=1.0 sets the zoom level to 100% when the page loads.

Tip: Do not add maximum-scale=1 or user-scalable=no. They stop users from zooming, which is an accessibility problem for people with low vision.

2. Why mobile first?

On a phone, most content is simply stacked in one column. This is the simplest layout, and it is what the browser does by default with block elements. So it is easier to start with one column and add columns when there is more space than to start with a complex desktop layout and undo it for small screens. Mobile first also makes you decide what content really matters, because a phone screen has little space.

II. Relative units

Fixed widths such as width: 1200px are the first cause of horizontal scrolling on phones. Prefer units that are relative to the parent, the font size or the viewport:

Unit Relative to Typical use
% The size of the parent element Widths of columns and images
rem The font size of the root element (html), 16px by default Font sizes, padding, margins, gaps
em The font size of the element itself Padding of buttons that should grow with their text
vw / vh 1% of the viewport width / height Full-screen hero sections, fluid font sizes
dvh 1% of the dynamic viewport height (accounts for the mobile address bar) Full-height sections on phones
fr A fraction of the free space in a grid container Grid columns
ch The width of the "0" character Limiting the length of text lines 
/* Make width and height include padding and border (avoids overflow surprises) */
*,
*::before,
*::after {
  box-sizing: border-box;
}

.Container {
  width: 90%;          /* fluid width ...                       */
  max-width: 1200px;   /* ... but never wider than 1200px       */
  margin: 0 auto;      /* centered                              */
  padding: 1rem;
}

.Article p {
  max-width: 70ch;     /* comfortable line length for reading   */
  line-height: 1.6;
}

.Hero {
  min-height: 100vh;   /* fallback for old browsers             */
  min-height: 100dvh;  /* full screen, even with the address bar */
}

h1 {
  /* clamp(minimum, preferred, maximum): the title grows with the screen
     but never becomes smaller than 1.8rem or larger than 3.5rem */
  font-size: clamp(1.8rem, 4vw + 1rem, 3.5rem);
}
Tip: Use max-width instead of width whenever you can. max-width: 1200px means "up to 1200px" and still lets the element shrink on a small screen, while width: 1200px forces it to be 1200px wide everywhere.

III. Media queries and breakpoints

A media query wraps CSS rules that only apply when its condition is true. The most common media features are min-width (the viewport is at least this wide) and max-width (the viewport is at most this wide). You can combine conditions with and, or list alternatives separated by commas. 

@media (min-width: 768px) { /* tablets and larger */ }

@media (min-width: 768px) and (max-width: 1023px) { /* tablets only */ }

@media (orientation: landscape) { /* wider than tall */ }

@media print { /* when the page is printed */ }

@media (prefers-color-scheme: dark) { /* the user's system uses a dark theme */ }

1. Desktop first (max-width) vs mobile first (min-width)

The Lab 2 demo site was written desktop first: the desktop styles are in Trip.css, and the file Trip_Responsive.css overrides them with max-width: 850px for small screens: 

/* Trip.css (desktop styles) */
.Trip_Cards {
  display: flex;
  justify-content: space-between;
}
.Trip_Card {
  width: 32%;
}

/* Trip_Responsive.css (undo the desktop layout on small screens) */
@media screen and (max-width: 850px) {
  .Trip {
    margin: 4rem 2rem;
  }
  .Trip_Cards {
    flex-direction: column;
  }
  .Trip_Card {
    width: 100%;
    margin-bottom: 1.5rem;
  }
}

This works, but you write the layout and then write it again to cancel it. Here is the same component written mobile first: the default styles are for phones, and the media query adds the three-column layout when there is enough room. 

/* Base styles = phones */
.Trip {
  margin: 4rem 2rem;
}
.Trip_Cards {
  display: flex;
  flex-direction: column;
  gap: 1.5rem;
}

/* From 850px and up: three cards side by side */
@media (min-width: 850px) {
  .Trip {
    margin: 4rem 6rem;
  }
  .Trip_Cards {
    flex-direction: row;
  }
  .Trip_Card {
    flex: 1;   /* each card takes an equal share of the row */
  }
}

2. Choosing breakpoints

There are too many devices to target each one. Instead, start with a narrow window, widen it slowly, and add a breakpoint where your content starts to look wrong (lines that are too long, cards that are too wide, a menu that no longer fits). As a starting point, these values are common:

  • Base styles: phones (no media query)
  • min-width: 600px large phones / small tablets
  • min-width: 768px tablets
  • min-width: 1024px laptops
  • min-width: 1280px large screens

Use the same few breakpoints in all the CSS files of your project, so that all the components of a page change at the same time.

Tip: Media queries do not increase specificity. Always place a media query after the rules it overrides (or link the responsive file after the main one, as the Lab 2 page does with ../Lab_3/*_Responsive.css), otherwise the later rule wins.

IV. Flexbox and Grid layouts that reflow

Flexbox and Grid (see FlexBox and Grid in the lecture) can often make a layout responsive with no media query at all, because they let items wrap or create as many columns as fit.

1. Flexbox with flex-wrap

.Cards {
  display: flex;
  flex-wrap: wrap;   /* items go to the next line when there is no more room */
  gap: 1.5rem;
}

.Card {
  flex: 1 1 250px;   /* grow, shrink, and try to be 250px wide */
}

On a 360px phone each card takes a full line; on a 1200px screen four cards fit in a row. The browser computes this for you.

2. Grid with auto-fit and minmax()

.Gallery {
  display: grid;
  /* as many columns as fit, each at least 220px, sharing the free space */
  grid-template-columns: repeat(auto-fit, minmax(220px, 1fr));
  gap: 1rem;
}
Tip: This course website uses the same technique: the cards on the hub pages use repeat(auto-fill, minmax(260px, 1fr)) (class .Hub_Grid in SRC/CSS/Styles.css). Resize your window on the home page to see the columns change.

3. Rearranging a page layout with grid-template-areas

For the overall page layout (header, sidebar, content, footer), named grid areas make it easy to describe a different layout for each breakpoint: 

<body class="Page">
  <header class="Page_Header">...</header>
  <aside class="Page_Sidebar">...</aside>
  <main class="Page_Content">...</main>
  <footer class="Page_Footer">...</footer>
</body>
        
.Page_Header  { grid-area: header; }
.Page_Sidebar { grid-area: sidebar; }
.Page_Content { grid-area: content; }
.Page_Footer  { grid-area: footer; }

/* Phones: everything in one column, sidebar after the content */
.Page {
  display: grid;
  grid-template-columns: 1fr;
  grid-template-areas:
    "header"
    "content"
    "sidebar"
    "footer";
  gap: 1rem;
}

/* Laptops: sidebar on the left */
@media (min-width: 1024px) {
  .Page {
    grid-template-columns: 250px 1fr;
    grid-template-areas:
      "header  header"
      "sidebar content"
      "footer  footer";
  }
}

4. Changing the order with flex-direction

In Destination_Responsive.css, each destination (image + text side by side on desktop) becomes a column on small screens with flex-direction: column-reverse, so the image always appears above its text even in the "reverse" items. You can also use the order property to move one item. 

@media screen and (max-width: 850px) {
  .Destination_Item,
  .Destination_Item_Reverse {
    display: flex;
    flex-direction: column-reverse;
    margin-top: 2.5rem;
  }

  .Destination_Text,
  .Destination_Image {
    width: 100%;
  }
}

V. Responsive images and media

1. Images that never overflow

An image is displayed at its natural size by default; a 1920px photo will overflow a 360px phone screen. Add this rule at the top of your main CSS file: 

img,
video,
iframe {
  max-width: 100%;   /* never wider than the container */
  height: auto;      /* keep the aspect ratio           */
  display: block;
}

/* Cover a fixed-size box without distorting the picture (cards, sliders) */
.Card img {
  width: 100%;
  aspect-ratio: 16 / 9;
  object-fit: cover;
}

2. srcset and sizes: let the browser pick the right file

Downloading a 3MB photo on a phone wastes data and time. Export a few versions of the same image at different widths, and describe them with srcset. The sizes attribute tells the browser how wide the image will be displayed, so it can choose the smallest file that is sharp enough. Always keep a src as a fallback and set width/height to avoid layout jumps while the image loads. 

<img src="assets/Images/Oran-800.jpg"
     srcset="assets/Images/Oran-480.jpg 480w,
             assets/Images/Oran-800.jpg 800w,
             assets/Images/Oran-1280.jpg 1280w"
     sizes="(min-width: 1024px) 50vw, 100vw"
     width="1280" height="720"
     alt="The Santa Cruz fort overlooking Oran"
     loading="lazy" />

3. picture: a different image per breakpoint

When you want a different crop (not just a different size), for example a square photo on phones and a wide banner on desktop, use <picture>. The browser uses the first <source> whose media query matches, otherwise the <img>. 

<picture>
  <source media="(min-width: 1024px)" srcset="assets/Images/Banner-wide.webp" />
  <source media="(min-width: 600px)" srcset="assets/Images/Banner-medium.webp" />
  <img src="assets/Images/Banner-square.jpg" alt="Our team at ENSIA" />
</picture>
Tip: Compress your images (WebP is usually much smaller than JPG/PNG) and add loading="lazy" to images that are below the first screen. Never use an image to display text: it cannot be resized, translated or read by screen readers.

VI. A responsive navigation bar with a hamburger menu

On a large screen, the menu links are displayed in a row. On a phone they do not fit, so we hide them behind a "hamburger" icon () and show them in a column when the user taps it. We present two versions: one with no JavaScript at all, and the one used in the Lab 2 demo site.

1. Version A: CSS only (checkbox hack)

A hidden checkbox stores the "open/closed" state. Clicking the <label> (the hamburger icon) checks or unchecks it, and the selector :checked ~ .Menu shows the menu that follows it. 

<nav class="Navbar">
  <a href="index.php" class="Logo">MyProject</a>

  <input type="checkbox" id="Menu_Toggle" class="Menu_Toggle" />
  <label for="Menu_Toggle" class="Menu_Icon" aria-label="Open the menu">
    <i class="fa-solid fa-bars"></i>
  </label>

  <ul class="Menu">
    <li><a href="index.php">Home</a></li>
    <li><a href="services.php">Services</a></li>
    <li><a href="about.php">About us</a></li>
    <li><a href="contact.php">Contact</a></li>
  </ul>
</nav>
        
/* ---------- Base styles: phones ---------- */
.Navbar {
  display: flex;
  flex-wrap: wrap;                 /* the menu can go on its own line */
  align-items: center;
  justify-content: space-between;
  padding: 1rem;
}

/* Hide the checkbox visually but keep it usable with the keyboard */
.Menu_Toggle {
  position: absolute;
  opacity: 0;
  pointer-events: none;
}

.Menu_Icon {
  font-size: 1.5rem;
  padding: 0.5rem;
  cursor: pointer;
}

.Menu_Toggle:focus-visible + .Menu_Icon {
  outline: 2px solid #8c1515;
}

.Menu {
  display: none;                   /* closed by default */
  flex-basis: 100%;                /* take a full line under the logo */
  flex-direction: column;
  list-style: none;
  margin: 0;
  padding: 0;
}

.Menu a {
  display: block;
  padding: 0.75rem 1rem;           /* big enough to tap with a finger */
  text-decoration: none;
}

/* Open state: the checkbox is checked */
.Menu_Toggle:checked ~ .Menu {
  display: flex;
}

/* ---------- Tablets and larger ---------- */
@media (min-width: 768px) {
  .Menu_Icon {
    display: none;                 /* no hamburger on large screens */
  }

  .Menu {
    display: flex;                 /* always visible */
    flex-basis: auto;
    flex-direction: row;
    gap: 1.5rem;
  }
}

2. Version B: a class toggled with a few lines of JavaScript (Lab 2 demo)

The Lab 2 demo site uses a .Menu_Icon that is hidden on desktop (Nav_Bar.css). In Nav_Bar_Responsive.css, below 850px, the icon is shown and the menu is moved off screen (right: -100%; opacity: 0;). When the menu has the class active, it slides in (right: 0; opacity: 1;) thanks to a CSS transition: 

@media screen and (max-width: 850px) {
  .Nav_Bar_Menu {
    display: flex;
    flex-direction: column;
    position: absolute;
    top: 0;
    right: -100%;               /* hidden outside the screen */
    width: 100%;
    opacity: 0;
    transition: 0.5s ease-in-out;
  }

  .Nav_Bar_Menu.active {
    right: 0;                   /* slides into the screen */
    opacity: 1;
  }

  .Menu_Icon {
    display: block;
    cursor: pointer;
  }
}

The JavaScript only has to add or remove the active class and swap the icon (the original file is Drop_Down_Menu.js). Here is a short, modern version. classList.toggle() returns true if the class was added, so we do not need a separate "clicked" variable: 

const menuIcon = document.querySelector("#Menu_Icon_ID");
const menu = document.querySelector("#Nav_Bar_Menu_ID");
const burgerIcon = document.querySelector("#Burger_Icon_ID");

menuIcon.addEventListener("click", () => {
  const isOpen = menu.classList.toggle("active");
  burgerIcon.className = isOpen ? "fas fa-times" : "fas fa-bars";
  menuIcon.setAttribute("aria-expanded", String(isOpen));
});
Tip: For accessibility, the element the user clicks should be a real <button type="button"> (or a <label> for version A), not a plain <div>: buttons can be reached with the Tab key and activated with Enter or Space.

VII. Testing with the browser DevTools

You do not need ten phones to test your site. Chrome, Edge and Firefox all have a device mode (called "Responsive Design Mode" in Firefox):

  1. Open your page from XAMPP (for example http://localhost/your_project/) and press F12 (or Ctrl+Shift+I) to open the DevTools.
  2. Press Ctrl+Shift+M (or click the phone/tablet icon) to toggle the device toolbar.
  3. Choose a device in the list (for example a small phone around 360px wide, a tablet, a laptop), or select Responsive and drag the edge of the viewport to resize it continuously.
  4. Rotate the device to test the landscape orientation.
  5. Open the Elements panel and select an element: the Styles pane shows which media query each rule comes from, and which rules are crossed out (overridden).
  6. In Chrome/Edge, the "..." menu of the device toolbar has Show media queries: it draws a bar with all your breakpoints that you can click.

What to check on every page

  • There is no horizontal scrollbar at any width between 320px and 1920px.
  • Text is readable without zooming (body text of about 16px, i.e. 1rem) and lines are not too long on large screens.
  • Links and buttons are large enough to tap (around 44×44px) and not too close to each other.
  • Images are not stretched, cropped badly or overflowing.
  • The navigation menu opens and closes on small screens, and every link is reachable.
  • Forms and tables remain usable (inputs take the full width on phones; wide tables scroll inside their own container).
/* Debug trick: find the element that causes horizontal scrolling.
   Add this rule temporarily, look for the box that sticks out, then remove it. */
* {
  outline: 1px solid red;
}

/* A wide table can scroll inside its wrapper instead of breaking the page */
.Table_Wrapper {
  overflow-x: auto;
}
Tip: Device mode is a simulation. To test on your real phone, connect it to the same Wi-Fi network as your computer and open http://YOUR_PC_IP/your_project/ (find the IP address with the ipconfig command on Windows). You may need to allow Apache through the Windows firewall.

VIII. Your turn: make your project responsive

Work as a team, each member on the pages/components they are responsible for (see Lab 2). Commit and push your changes regularly.

  1. Viewport: check that every page (or your shared header file) contains the viewport meta tag.
  2. Reset: at the top of your main CSS file, add box-sizing: border-box for all elements and the img { max-width: 100%; height: auto; } rule.
  3. Agree on breakpoints: choose 2 or 3 breakpoints as a team (for example 768px and 1024px) and write them in your README so everyone uses the same values.
  4. Remove fixed widths: search your CSS for widths in px on containers and replace them with %, max-width, fr or flex. Replace font sizes in px with rem.
  5. Rewrite the layouts mobile first: for each component (cards, galleries, product lists, footer, ...), write the one-column version as the base style, then use @media (min-width: ...) to add columns. Use flex-wrap or repeat(auto-fit, minmax(...)) where possible.
  6. Navigation bar: implement a hamburger menu (version A or B of section VI) that appears below your first breakpoint.
  7. Images: compress the large images of your project and use srcset or <picture> for the biggest ones (hero, banners).
  8. Forms and tables: make inputs take 100% of the width on phones and wrap wide tables (for example your CRUD lists) in a container with overflow-x: auto.
  9. Test: go through every page in device mode at 360px, 768px, 1024px and 1440px, and apply the checklist of section VII. Fix every problem you find.
Tip: Compare your work with the Lab 2 demo site: open it in device mode, then read its responsive files (Nav_Bar, Hero, Destination, Trip, Footer).

Deliverables

  • Every page of your team project has the viewport meta tag.
  • All pages are responsive: they display correctly, with no horizontal scrolling, from 320px phones to large desktop screens.
  • The layouts use relative units and Flexbox/Grid, with media queries written mobile first and a common set of breakpoints.
  • The navigation bar collapses into a working hamburger menu on small screens.
  • Images scale with their container and large images are optimized.
  • The work is committed and pushed to your team repository. It counts toward the HTML/CSS milestone ("Build all the pages of the website in a responsive style"); see the Deadlines table in the syllabus for the date.
