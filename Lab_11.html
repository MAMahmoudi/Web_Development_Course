Lab 11: Final project integration and presentation

Instructions

This is the last lab of the semester. Your team will bring all the parts of the project together, check that everything works from a fresh installation, clean up the Git repository, write a README that lets anyone install and run your website, export the database, test the application end to end and prepare the final presentation. At the end of this lab, a person who has never seen your project should be able to clone it, follow the README and use every feature in less than 15 minutes.

I. Integration checklist

During the semester each member worked on separate pages and services. Integration means checking that these parts work together: shared navigation, shared CSS, one database connection file, one session system and consistent naming. Merge all the finished branches into main, then go through the following checklist together, on one machine, starting from a fresh clone.

Area What must work Related labs and lectures
Pages and layout All pages are reachable from the navigation bar, share the same style and are responsive (test at 360px, 768px and 1280px wide with the DevTools device toolbar). No broken links or images. CSS Layout
Validation Every form is validated in JavaScript (immediate feedback) and in PHP (security). Error messages are clear and shown next to the field. JS Form Validation
Web services At least 5 CRUD services work: create, read (list and detail), update and delete, with the results visible in phpMyAdmin. PHP and MySQL
Authentication Register, login, logout and session timeout work; pages reserved to logged-in users or admins redirect the others. Sessions and Cookies
AJAX The AJAX features (search, live update, pagination, ...) return valid JSON and update the page without reloading; errors are handled and shown to the user. AJAX
Security All the issues of the Lab 10 audit are fixed and closed: prepared statements, output escaping, CSRF tokens, password hashing, authorization checks, safe uploads, no secrets in Git. Lab 10, Security
Tip: look for paths that only work on one machine, such as C:\xampp\htdocs\... or http://localhost/ahmed_project/. Use relative paths (css/style.css) in HTML and __DIR__ in PHP includes (require __DIR__ . '/includes/db.php';).

II. Git workflow hygiene

The repository is part of the evaluation: it shows how the team worked. A clean history has one branch per feature, changes merged through pull requests reviewed by another member, small commits with meaningful messages, and contributions from every member.

Feature branches and pull requests

# Start a feature from an up-to-date main
git checkout main
git pull
git checkout -b feature/product-search

# Work, then commit small logical steps
git add products/search.php js/search.js
git commit -m "Add AJAX product search by name"

# Publish the branch and open a pull request on GitHub
git push -u origin feature/product-search

# Before merging, bring the latest main into your branch and fix conflicts locally
git checkout feature/product-search
git pull origin main

On GitHub, open the pull request from feature/product-search into main, describe what it does and how to test it, and ask a teammate to review it. Merge it only once it works on the reviewer's machine, then delete the branch.

Meaningful commit messages

Bad Good
update Add server-side validation to the registration form
fix Fix IDOR in edit_post.php: check that the post belongs to the user
final version 2 Make the product grid responsive below 768px

Check that everyone contributes

# Number of commits per author on main
git shortlog -sn main

# Same, ignoring merge commits
git shortlog -sn --no-merges main

# A compact view of the history and its branches
git log --oneline --graph --all -20
Tip: if the same person appears under two names (for example a laptop and a lab computer configured differently), fix your identity with git config --global user.name "First Last" and git config --global user.email "you@example.com", using the email of your GitHub account. Commits made from another member's computer are counted for that member.

III. Writing a good README.md

The README.md file is displayed on the home page of your GitHub repository. It is the first thing a teacher, a classmate or a future employer reads. It must explain what the project does and, above all, how to install it. Use the following template and replace every line between angle brackets. Screenshots go in a folder of the repository (for example docs/screenshots/). 

# <Project name>

<One or two sentences: what the website does and for whom.>

## Team
- <Member 1> - <main responsibilities, e.g. products pages and product services>
- <Member 2> - <...>
- <Member 3> - <...>

## Features
- User registration, login and logout
- <Service 1: e.g. create, edit and delete products (admin)>
- <Service 2: e.g. live search of products with AJAX>
- <...>

## Screenshots

## Technologies
HTML, CSS, JavaScript, PHP 8, MySQL (MariaDB), XAMPP

## Installation
1. Install XAMPP and start **Apache** and **MySQL** from the XAMPP control panel.
2. Clone the repository into the `htdocs` folder:
   `git clone https://github.com/<organization>/<repository>.git C:/xampp/htdocs/<repository>`
3. Open http://localhost/phpmyadmin, click **Import**, choose `database/<database>.sql` and click **Import**
   (the file creates the database and its tables).
4. Copy `config.example.php` to `config.php` and fill in your database credentials.
5. Open http://localhost/<repository>/ in your browser.

IV. Exporting the database

Your PHP code is useless without the database. Export it into a .sql file and commit it in a database/ folder, so that anyone can recreate it. Export the final version, after all the structure changes of the semester.

  1. Open http://localhost/phpmyadmin and select your database in the left panel.
  2. Click the Export tab and choose the Custom export method.
  3. Keep the format SQL, select all the tables, and in "Object creation options" check Add CREATE DATABASE / USE statement and Add DROP TABLE.
  4. Click Export and save the file as database/<database>.sql in your repository.

You can do the same from the command line with the tools shipped with XAMPP (in Git Bash): 

# Export (structure + data, with CREATE DATABASE)
/c/xampp/mysql/bin/mysqldump -u root -p --databases shop > database/shop.sql

# Import on another machine
/c/xampp/mysql/bin/mysql -u root -p < database/shop.sql

Before exporting, clean the data: remove personal information and junk test rows, and keep a small but realistic data set (a few users, products, comments...) so the demo looks alive. To create the hash of a test account password, run the following command and paste the result in the password_hash column with phpMyAdmin: 

/c/xampp/php/php -r "echo password_hash('Admin1234!', PASSWORD_DEFAULT), PHP_EOL;"
        
-- Or insert the test accounts directly (replace the hashes with the ones you generated)
INSERT INTO users (name, email, password_hash, role) VALUES
  ('Admin', 'admin@test.local', '$2y$10$...generated hash...', 'admin'),
  ('Test User', 'user@test.local', '$2y$10$...generated hash...', 'user');
Test it: drop your local database (or use a teammate's computer), import the .sql file, and check that the whole site works. If the import fails, the reviewers' import will fail too.

V. End-to-end testing

End-to-end testing means using the application like a real user, from the browser to the database and back. Write a short manual test plan (for example in docs/TEST_PLAN.md) with one line per scenario, and run it on a fresh installation. Each member tests the services written by someone else.

# Scenario Steps Expected result Result
1 Register a new user Open the register page, fill valid data, submit Redirected to the home page, logged in; new row in the users table with a hashed password Pass / Fail
2 Invalid registration Submit with an empty name and an invalid email; then disable JS and submit again JS errors shown; with JS disabled, PHP rejects the data with a message Pass / Fail
3 Create / edit / delete an item Log in as admin, create an item, edit it, delete it Each change visible on the page and in phpMyAdmin Pass / Fail
4 Access control Log out and open an admin URL; log in as a user and open another user's edit URL Redirected to login / "Access denied" Pass / Fail
5 AJAX search Type in the search field Results update without reloading; "no result" message when nothing matches Pass / Fail

Browser DevTools

Open the DevTools (F12) on every page while you test. The Console tab must show no red errors (JavaScript errors, blocked resources, CSP violations). In the Network tab, no request should fail (status 404 or 500), and AJAX responses should contain valid JSON, not PHP warnings mixed with the data.

HTML validation and Lighthouse

Check your HTML with the W3C validator at https://validator.w3.org/. Since your pages are generated by PHP on localhost, open a page, view its source (Ctrl+U), copy it and use the "Validate by Direct Input" tab. Fix the errors (unclosed tags, duplicate ids, missing alt attributes...). Then run Lighthouse (DevTools > Lighthouse tab, mode "Navigation") on your main pages for mobile and desktop, and use the report to improve performance, accessibility and best practices (image sizes, contrast, labels on form fields).

Tip: test in at least two browsers (for example Chrome and Firefox) and on a real phone connected to the same network, using your computer's IP address instead of localhost.

VI. Optional: deploying online

Deployment is not required, but a public URL is a great addition to your README and your CV. Any shared hosting or free PHP hosting service with MySQL works the same way:

  1. Create an account and a website on the hosting service; note the FTP credentials and the database host, name, user and password it gives you.
  2. Create the database in the hosting control panel, open its phpMyAdmin and import your .sql file. If the import fails because of the CREATE DATABASE statement, export again without it (shared hosting usually imposes the database name).
  3. Upload your files (without the .git folder) into the public folder (often htdocs or public_html) with the hosting file manager or an FTP client.
  4. Create config.php on the server with the hosting database credentials and 'production' => true.
  5. Turn off display_errors, enable HTTPS if the host offers it, then rerun your test plan on the online version.
Warning: a public site will be visited by bots that try common attacks. Deploy only after the Lab 10 fixes, never with the default test passwords, and never with real personal data.

VII. Final presentation

The final presentation is a 10 to 15 minute demonstration of your project followed by questions. Every member must present the part they built and be able to explain its code: the evaluation is individual as well as collective. A suggested structure:

Part Duration Content
Introduction 1-2 min The problem, the target users, the team and who did what.
Architecture 2 min Database schema (tables and relations), folder structure, list of the web services.
Live demo 5-8 min A realistic user scenario that goes through the main CRUD services, authentication and AJAX. Each member demonstrates their own features. Show the responsive layout on a small screen.
Security and quality 1-2 min Main findings of the security audit and how they were fixed; testing done.
Conclusion 1 min Difficulties met, what you learned, possible improvements.

Prepare the demo

  • Rehearse the full presentation at least once with a timer.
  • Prepare the demo data and the accounts in advance; log out of everything before you start.
  • Record a short backup video of the demo (screen recording) in case the network, the laptop or XAMPP fails on the day.
  • Have the project working on two laptops, and keep the code open in your editor to answer questions.
  • Zoom the browser and the editor (Ctrl and +) so the audience can read.

Questions you should be ready to answer

  • Show the code of one of your services: what happens from the click in the browser to the database?
  • Why do you validate the data in PHP if JavaScript already validates it?
  • How do you protect this query against SQL injection? This page against XSS? This form against CSRF?
  • How are passwords stored? What happens to the session at login and logout?
  • What can a user do if they change the id in the URL?
  • What does this AJAX request send and receive? Show it in the Network tab.
  • How did you organize the work in Git? Show a pull request you reviewed.
  • What would you change if you had to start again?
Further reading: documentation, tools and tutorials for going further are collected on the Resources page.

Deliverables

  • The integrated project merged into main on GitHub, with all features of the integration checklist working from a fresh clone.
  • A complete README.md: description, features, screenshots, installation steps and test accounts.
  • The database dump in database/, importable with phpMyAdmin.
  • The manual test plan with its results, a console free of errors and the W3C validation errors fixed.
  • A clean Git history: feature branches, pull requests, meaningful commits and contributions from every member (git shortlog -sn).
  • The final presentation with a live demo and a backup video. It corresponds to the "Final project presentation" row of the Deadlines table in the Syllabus.
